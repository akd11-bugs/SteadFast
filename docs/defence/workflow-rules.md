# Defence brief: workflow rules

## 1. What it does

An admin opens Settings and builds rules of the form "when a lead's stage changes to X, do Y" (`components/settings/WorkflowRulesCard.tsx:35-38`). The card is shown only to admins (`components/settings/SettingsTabs.tsx:144`). There are three actions:
- create a task, with an optional due date in N days
- send an email to the lead or to the rule's owner
- POST a signed JSON payload to a webhook (`lib/workflow.ts:78-175`)

Each rule belongs to the user who created it (`app/api/workflow-rules/route.ts:94`). It fires only for leads that user owns (`lib/workflow.ts:57-59`). It fires on every stage change that goes through `applyStageChange`, right after the change is saved (`lib/leadStage.ts:128,157-161`):

| Path | Code |
|---|---|
| Lead detail / Kanban | `app/api/leads/[id]/route.ts:86` |
| Bulk change | `app/api/leads/bulk/route.ts:83` |
| Field rep portal | `app/api/rep/leads/[id]/route.ts:90` |
| Agent API | `app/api/agent/v1/leads/[id]/stage/route.ts:50` |
| MCP | `lib/mcp/tools.ts:311` |
| Sheet-sync review | `app/api/jobs/[jobRunId]/issues/[issueId]/resolve/route.ts:73` |

Results show on the lead's activity feed as "Automation — <rule name>" (`lib/workflow.ts:40-49`).

## 2. Why X instead of Y

| Decision | Rejected alternative | Why |
|---|---|---|
| Evaluated inline from `applyStageChange` (`lib/workflow.ts:51-55`) | An event bus or job queue | There is only one trigger type (`app/api/workflow-rules/route.ts:10`). A bus would be unused abstraction. |
| Fire-and-forget, with no `await` on the rules (`lib/leadStage.ts:157-161`) | Awaiting the rules inside the stage update | A broken rule (for example, bad email config) must not fail a stage change that already succeeded. |
| One rule's failure does not stop the others. The failure is written to the lead (`lib/workflow.ts:61-75`) | Logging to the console only | The user can see that nothing was sent. |
| Trigger and action config stored as JSON strings (`prisma/schema.prisma:418-421`) | A table per action type | New action types need no migration. The cost is that the server does not check the shape (see section 5). |
| Webhook creation is admin only (`app/api/workflow-rules/route.ts:65-70`) | Letting anyone create webhooks | A webhook makes the server fetch a user-chosen URL, which is an SSRF risk. Tasks and emails only touch the org's own data. |
| Signing secret generated by the server and shown once (`route.ts:78-83,97`). Stored encrypted and stripped from reads (`route.ts:13-20`) | A secret supplied by the client | Same pattern as the app's other API-key-shaped secrets. |
| URL checked at save time **and** at fire time, with `redirect: 'manual'` and a 5-second timeout (`lib/workflow.ts:139-158`, `route.ts:72-77`) | Checking only at save time | Blocks DNS rebinding and redirects to internal addresses. |
| Emails sent "as" the rule owner (`lib/workflow.ts:109`, `lib/email.ts:134-189`) | Always using one shared mailbox | Replies reach the rep. Falls back to the org mailbox, then the global mailbox (`lib/email.ts:141-149`). |

## 3. Malicious actors

| Actor | What they can try | What stops them |
|---|---|---|
| Anonymous visitor | Create, list, toggle or delete rules | `requireApiUser` on every handler (`app/api/workflow-rules/route.ts:35,45`, `[id]/route.ts:9,26`). |
| Anonymous visitor | Trigger a rule indirectly | Only a stage change triggers rules, and every caller listed in section 1 is authenticated. No lead-create path calls `evaluateStageRules`; only `lib/leadStage.ts:160` does. |
| Sales rep | Create a webhook | 403 (`route.ts:70`). |
| Sales rep | Create email or task rules through the API, even though the card is hidden from them (`SettingsTabs.tsx:144`) | **Not stopped.** POST has no role check for these action types (`route.ts:44-60,86-96`). Effect: emails go to their own leads, sent from their own mailbox. That is the same reach they have by hand, but it is automated across a bulk stage change (`bulk/route.ts:82-97`). |
| Sales rep | Edit or delete another user's rule | `findFirst` on `{id, orgId, ownerId: user.id}`, returning 404 (`[id]/route.ts:15-16,29-30`). |
| Admin of another org | Read or modify our rules by id | Every query is filtered by session `orgId` and `ownerId` (`route.ts:38`, `[id]/route.ts:15,29`). `orgId` comes from the session (`route.ts:88`). |
| Admin of another org | Have our leads fire their rules | The evaluator filters on `lead.orgId` and `lead.ownerId` (`lib/workflow.ts:57-59`). |
| Admin (own org) | Use a webhook for SSRF | `assertSafeWebhookUrl` at save and fire time (`lib/ssrfGuard.ts:47`, `lib/workflow.ts:152`). Redirects are refused (`:157,160-162`). The guard blocks loopback (incl. `::`), RFC1918, link-local/metadata, `100.64/10`, and IPv4-mapped IPv6 in either notation (`lib/ssrfGuard.test.ts`). The same guard now protects MCP connection URLs (`lib/mcp/connections.ts`). A narrow DNS-rebinding race remains, as the code itself documents (`:147-151`). |
| Someone who can edit the connected sheet | Fire rules by importing leads | Import creates leads directly and fires no rules (`lib/leadImport.ts:264-275`). But a stage they wrote that does not map becomes an issue. When an admin or operations user resolves it, the lead owner's rules fire (`resolve/route.ts:73-78`). The stage is still chosen and validated by a human (`resolve/route.ts:62-65`). |
| Holder of a leaked cron secret | Fire rules | The sync cron only creates leads (`app/api/cron/sync-leads-sheet/route.ts:121`) and never calls `applyStageChange`, so it cannot fire rules. |

**Residual risks:**
- **Admins cannot see or switch off other users' rules.** GET returns only the caller's own rules (`route.ts:38`), and PATCH/DELETE require `ownerId: user.id` (`[id]/route.ts:15,29`).
- **A deactivated user's rules keep firing.** The evaluator never checks whether the owner is active (`lib/workflow.ts:57-59`), and neither does `sendEmailAs` (`lib/email.ts:135-138`). No deactivation code touches `workflowRule`. Whether their leads get reassigned is unverified.
- **Webhook payloads send the lead's email and company to the configured URL** (`lib/workflow.ts:123-129`).
- **Error text from the Gmail API is written into a lead note** that anyone who can see the lead can read (`lib/workflow.ts:72`, `lib/email.ts:185`).

## 4. Data structures

`WorkflowRule` (`prisma/schema.prisma:414-427`):

| Field | Shape and why |
|---|---|
| `orgId` (`:416`) | The tenant boundary. A plain string with no relation. |
| `triggerType` (`:418`) | A string. Only `stage_changed` is accepted (`route.ts:10,52`). |
| `triggerConfig` (`:419`) | JSON string such as `{"toStage":"..."}`. Parsed defensively; bad JSON means "no match" (`lib/workflow.ts:29-35,62-63`). |
| `actionType` (`:420`) | `create_task`, `send_email` or `call_webhook` (`route.ts:11`). The schema comment omits `call_webhook`. |
| `actionConfig` (`:421`) | JSON string. For webhooks it holds `url` and `signingSecretEnc` (`route.ts:83`). Other actions store whatever object the client sent. |
| `ownerId` (`:422`) | A plain string with no foreign key, the same convention as `Task.ownerId`. It decides both whose leads trigger the rule and whose mailbox sends. |
| `active` (`:423`) | The only field PATCH can change (`[id]/route.ts:18-21`). |
| `@@index([orgId, ownerId, triggerType, active])` (`:426`) | Matches the evaluator's `where` clause exactly (`lib/workflow.ts:58`), so each stage change is one indexed lookup. |

Side effects write to `Task` (`lib/workflow.ts:82-91`, with `source: 'sequence'`), `Activity`, and `Lead.lastActivityAt` (`:45-48`).

## 5. Where it fails

| Failure | What the user sees | How we notice |
|---|---|---|
| Rule targets a custom stage | The card offers only the 5 built-in stages (`WorkflowRulesCard.tsx:12,221`, `lib/types.ts:137`). The API never checks `toStage` (`route.ts:58`), so a rule for a missing stage never fires. | Nothing. It fails silently. |
| Lead has no email (`to: lead`) | No email and no activity entry (`lib/workflow.ts:100-105`) | Nothing. Covered by `lib/workflow.test.ts:152`. |
| Email send throws | A lead note: "Automation failed (send_email) — nothing was sent: ..." (`lib/workflow.ts:70-73`) | The note, plus the server log (`:69`). |
| Webhook is down, slow, redirects or is blocked | Nothing on the lead. Only a success writes a note (`lib/workflow.ts:160-173`) | Server log only. There is no retry and no delivery log (`:132-137`). |
| Process restarts before a rule finishes | The action is lost. It was never awaited (`lib/leadStage.ts:160`). | Nothing. |
| `triggerConfig: null` sent through the API | Accepted, because `typeof null === 'object'` (`route.ts:58`). The card then reads `rule.triggerConfig.toStage` (`WorkflowRulesCard.tsx:36`) and probably crashes. | Unverified at runtime. |
| `dueInDays` very large | An invalid `Date` makes the task insert throw, which becomes a failure note (`lib/workflow.ts:87`, `:66-74`) | The note. |
| Lead is reassigned | The new owner's rules now apply. The comment says "acting rep's" rules (`lib/workflow.ts:52`), but the code uses `lead.ownerId` (`:58`). | Doc and code disagree. |
| Bulk stage change on N leads | The stage changes run one after another (`bulk/route.ts:79-82`), but each lead's rules start without waiting. So N emails go out close together. | Gmail rate limits are unverified. |

**Accepted limits (`shortcut:`):** the Gmail client cache used for rule emails is per process and never evicted (`lib/email.ts:110-112`). There are no other `shortcut:` comments in the rules code.
